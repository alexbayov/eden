# 23 — Контракты данных и контентный pipeline

**Статус:** 🟢 v1.0, 22 августа 2026. Описывает **фактическое** состояние контрактов в `code/` и правила их изменения.

Тикеты, меняющие эти контракты, — в [`22-developer-work-packages.md`](22-developer-work-packages.md). Проверки — в [`24-test-matrix-and-release-gates.md`](24-test-matrix-and-release-gates.md).

---

## 1. Принципы

1. **Данные отдельно от кода.** Контент живёт в `code/public/config/*.json` и загружается в runtime. Добавление контента не требует изменения кода.
2. **Валидация до использования.** Каталог проверяется целиком, включая cross-references, **до** создания кампании и сохранения. Невалидный контент — явная ошибка с путём и причиной, а не падение в середине игры.
3. **Один envelope на все виды контента.** `contentVersion` + `kind` + `entries` для коллекций.
4. **Ни одного магического значения в двух местах.** Если число нужно и коду, и данным — источник один.
5. **Отказ громче догадки.** Невалидное поле отклоняется, а не нормализуется молча. Исключение — явная документированная миграция.
6. **Тест на каждый инвариант.** Инвариант без падающего теста считается несуществующим.

## 2. Реализованный envelope контента

Источник: `code/src/game/content-format.ts`.

```ts
export const CONTENT_VERSION = 1
```

Правила:

| Правило | Реализация | Поведение |
|---|---|---|
| Отсутствие `contentVersion` | `migrateContent` | трактуется как v1 |
| Любая версия ≠ 1 | `checkEnvelope` | ошибка `version`, путь `$.contentVersion` |
| Не объект на верхнем уровне | `checkEnvelope` | ошибка `shape`, путь `$` |
| Несовпадение `kind` | `checkEntries` | ошибка, путь `$.kind` |
| Пустой `entries` | `checkEntries` | ошибка, путь `$.entries` |
| Дублирующийся `id` | `checkUniqueIds` | ошибка, путь `$.entries[<id>]` |

Формат ошибки одинаков для всех видов контента:

```ts
class ContentValidationError extends Error {
  code: 'parse' | 'version' | 'shape'
  issues: { path: string; message: string }[]
}
```

Сообщения — на русском, путь — в JSONPath-подобной нотации (`$.entries[2].cost.metal`). Оба свойства обязательны для новых валидаторов.

## 4. Cross-reference контракт

Источник: `validateCampaignCatalog` (`campaign-content.ts`) и `validateEquipmentReferences` (`content.ts`).

Проверяется **до** использования каталога:

| Ссылка | Требование | Ошибка |
|---|---|---|
| `save.character.level` → кривая `progression` | уровень равен `levelForXp(xp)` по загруженной кривой | `$.character.level` |
| `save.character.unspentSkillPoints` → кривая `progression` | не больше суммы `skillPoints` достигнутых уровней | `$.character.unspentSkillPoints` |
| `save.character.xp` → `save.campaign.xp` | совпадают: XP имеет один дом | `$.character.xp` |
| `mission.zoneId` → `zones` | зона существует | `missions.<id>.zoneId` |
| `mission.arenaId` → arena catalog | карта существует | `missions.<id>.arenaId` |
| `mission.rewardId` → `rewards` | награда существует | `missions.<id>.rewardId` |
| `recipe.output.itemId` → `items` | предмет существует | `recipes.<id>.output.itemId` |
| `reward.items[].id` → `items` | предмет существует | `rewards.<id>.items.<itemId>` |
| зона → её encounter | зона содержит хотя бы один encounter | `zones.<id>` |
| порядок encounter внутри зоны | строго последовательный с 1, без разрывов | `missions.<id>.order` |
| `unit.archetypeId` → `equipment.enemies` | архетип существует | `arenas.<id>.units[i].archetypeId` |
| `archetype.weaponId` → `equipment.weapons` | оружие существует | `...weapon.weaponId` |
| `weapon.ammoId` → `equipment.ammo` | патрон существует и **совпадает** с definition | `...weaponState.ammoId` |
| `armorId` (в т.ч. составной) → `equipment.armor` | каждая часть существует | `...armor.armorId` |
| manifest ↔ загруженные карты | множества `id` совпадают | `arenas` |
| arena catalog ↔ `mission.arenaId` | каталог покрывает все нужные карты | `arenas` |
| id в manifest ↔ id внутри файла карты | совпадают | `$.entries.<id>` |

**Правило для нового контента:** любая новая ссылка между сущностями обязана попасть в эту таблицу и в cross-reference валидатор. Ссылка, проверяемая только в runtime «по факту использования», считается дефектом.

## 5. Контракт сохранения

Источник: `code/src/game/save.ts`.

### 5.1 Текущая схема

| Параметр | Значение |
|---|---|
| Версия | `SAVE_SCHEMA_VERSION = 6` (было 5 до `W6-01`, 25 августа 2026) |
| Ключ | `eden.save.v6` |
| Ключ резервной копии | `eden.save.v6.corrupt-backup` |
| Ключи прошлых версий (только чтение) | `LEGACY_SAVE_STORAGE_KEYS = ['eden.save.v5', 'eden.save.v4']` |
| Поддерживаемые миграции | v5 → v6 (`normalizeV6`), v4 → v5 → v6, v3 → v4 → v5 → v6 — все только с валидированным каталогом |
| Валидация v6 | strict cross-field, без изменения версии |

Структура: `{ schemaVersion, arenaId, activeEncounterId, phase, turn, rngState, units, campaign, character, inventory, base, objective }`.

**`objective` (v6, `W6-01`):** `{ heldTurns, carrying }` — единственные два факта о цели, которые нельзя восстановить с доски. Всё остальное, что нужно цели (живые враги, позиция героя, номер хода), уже лежит в этом же сохранении, и копировать это сюда означало бы создать второй источник истины, способный разойтись с `units`.

Два правила валидации, и оба неочевидны:

1. **`heldTurns` проверяется, а не берётся на доверии.** `evaluateObjective` сравнивает его с `holdTurns` миссии и **не** перевыводит из доски — то есть отредактированное вручную значение это бесплатное прохождение. То же для `carrying` и доставки.
2. **Вне активной миссии состояние обязано быть нулевым.** Сохранение на базе с `carrying: true` выдало бы игроку уже доставленный груз в момент старта следующей retrieval-миссии, а ненулевой `heldTurns` — прогресс удержания, унаследованный от прошлой цели.

**Почему нужен список ключей прошлых версий.** Правило §5.3 п.2 требует нового ключа хранилища при повышении версии. Само по себе это делает сохранение существующего игрока **невидимым**: приложение прочитало бы пустой `eden.save.v5` и начало новую кампанию, а игрок увидел бы потерю прогресса, а не миграцию. Поэтому адаптер читает ключи по порядку «текущий, затем прошлые», миграет найденное и **записывает результат под текущим ключом на этапе boot** (`hasPendingUpgrade()` в `SaveAdapter`). Старый ключ **не удаляется**: неудачное обновление остаётся откатываемым. `reset()`, наоборот, чистит все слоты — иначе прошлый payload воскрес бы при следующей загрузке.

### 5.2 Реализованные инварианты

**Фазы и экраны:**

| Экран | Допустимые фазы |
|---|---|
| `home`, `mission-select` | только `player` |
| `mission` | `player` или `enemy` |
| `reward` | только `victory` |
| `return` | только `defeat` |

Смысл жёсткости: терминальные фазы существуют только на явных экранах результата, иначе глобальная боевая клавиша могла бы возобновить чужой ход после навигации.

**Кампания:** `catalogId` совпадает с каталогом; `encounters` точно покрывают каталог миссий без дублей и пропусков; первый encounter не может быть `locked`; encounter открывается только после `completed` предыдущего; `victories > 0` требует `completed`; `firstRewardClaimed` только у `completed`; `claimedRewards` уникальны, известны и принадлежат `completed` encounter; зона `completed` только когда все encounter `completed`; `xp` — конечное неотрицательное; `firstDeathReturnUsed` — boolean; `mission` — точная копия соответствующего encounter.

**`campaign.returnReason` (v5):** `defeat` | `retreat` на экране `return` и **строго** `null` вне него. Поле введено в W4-02, потому что до v5 отступление было буквально `missionDefeat` и два исхода были неразличимы в состоянии. Как только поражение стоит XP, это недопустимо: штраф начисляется при уходе с экрана возврата, и к этому моменту сказать, вывели оперативника из строя или он ушёл сам, может только сама кампания. Требование `null` вне экрана возврата — не косметика: устаревшее значение позже прочитал бы расчёт штрафа.

**Персонаж (v5, `$.character`):** `{ level, xp, unspentSkillPoints }`, все — неотрицательные целые. `level` в диапазоне `1..maxLevel(curve)` и **равен** `levelForXp(xp)` по загруженной кривой; `unspentSkillPoints` не больше суммы `skillPoints` достигнутых уровней; `xp` **совпадает** с `campaign.xp`.

Смысл: `level` и `unspentSkillPoints` — производные величины, поэтому сохранение согласовано только если кривая с ними согласна. Это закрывает очевидную правку руками (уровень 6 при 0 XP) и, что важнее, делает смену кривой обнаруживаемым рассогласованием сохранения, а не молча неверным уровнем на экране базы. Дублирование XP в двух полях существует потому, что прогрессия читает `character`, а все действующие правила награды и валидации читают `campaign.xp`; равенство проверяется, чтобы два поля не могли разойтись.

**Активная встреча:** `activeEncounterId === null` ⇔ `campaign.activeMissionId === null` и `activeMapId === null`; при активной встрече `arenaId` совпадает с ареной миссии из каталога.

**Инвентарь:** стаки имеют известные id, положительные целые количества, неотрицательный вес, **совпадающий с каталогом**; id уникальны в контейнере; ровно 4 quick slot, каждый — null или item, фактически присутствующий в backpack, без дублей; equipment имеет уникальные `instanceId`, известные `itemId`, корректный `slot` по типу (оружие в `primary`/`secondary`, броня в `head`/`torso` согласно definition), `0 ≤ durability ≤ maxDurability`.

**Юниты:** непустые `id`/`name`/`color`; `team` ∈ player\|enemy; целые `x`/`y`/`ap`/`aim`/`maxHp`; `0 ≤ hp ≤ maxHp`; валидные позы и статусы; уникальные id; **ровно один** `hero` в команде player.

**Связь бой ↔ инвентарь (для игрока):** `weaponState` ссылается на существующий equipment instance того же слота; **все** поля weapon definition кэшированы и совпадают с каталогом; `ammoId` совпадает с ammoId оружия; модификаторы патрона совпадают с definition; `armor.reduction` совпадает с definition по всем частям и **не содержит лишних** полей; durability брони синхронизирована с инвентарём.

Пустая броня врага (`armorId: ""` с пустым `reduction`) — допустимое исключение.

### 5.3 Правила изменения схемы

1. **Никогда** не менять смысл существующего поля. Новое поведение — новое поле.
2. Повышение версии требует: новый `SAVE_SCHEMA_VERSION`, новый ключ хранилища, функция миграции, таблица соответствия полей, тесты успеха **и** отказа.
3. Миграция обязана требовать валидированный каталог; миграция без каталога — отказ, а не догадка (уже реализовано для v3→v4).
4. Невалидный источник отклоняется **до** миграции.
5. Миграция только вперёд. Понижение версии не поддерживается; сохранение более новой версии отклоняется с понятным сообщением.
6. Повреждённое сохранение копируется в backup-ключ до сброса.
7. Ослабление любого инварианта из §5.2 требует явного обоснования в PR и обновления этого документа.

Таблица миграции v4 → v5 (`normalizeV5`, W4-05 ✅). Добавлено ровно два поля, ни одно существующее не переосмыслено:

| Поле v4 | Поле v5 | Правило | Дефолт |
|---|---|---|---|
| `campaign.xp` | `campaign.xp` | **приводится к целочисленному полу и нижней границе 0**, а не переносится как есть: `Math.floor(xp)` при конечном `xp >= 0`, иначе `0` | `0`, если поле не число, не конечно или отрицательно |
| — | `character.xp` | зеркалит уже приведённый `campaign.xp`, поэтому равенство двух полей — свойство миграции, а не отдельная проверка | приведённый `campaign.xp` |
| — | `character.level` | вычисляется из `xp` по загруженной кривой | `levelForXp(xp)` |
| — | `character.unspentSkillPoints` | всё, что начислили достигнутые уровни | `skillPointsGranted(level)` |
| — | `campaign.returnReason` | `'retreat'` на экране `return`, иначе `null` | см. ниже |

Все три поля `character` строит одна функция — `characterForXp(xp, curve)`, — поэтому миграция не может собрать `level`, не согласованный с `xp`: то же самое выражение позже проверяет валидатор.

**Про «пол XP» в первой строке.** Формально это единственное переосмысление существующего поля во всей миграции, и назвать его нужно прямо: v4 допускал дробный `xp`, v5 — нет, потому что `levelForXp` определён над целыми и дробный остаток не дал бы воспроизводимого уровня. Практического риска нет — ни один шиппящийся источник XP не выдаёт дробей (награды 30/45/60), — но у правки есть направление: она может только **понизить** XP, максимум на единицу, и никогда не повысить. Если в источнике оказался бы `NaN`, `Infinity` или отрицательный XP, миграция даст `0`, а не унаследует битое значение; сам такой источник до этого места, впрочем, обычно не доходит — он отклоняется валидацией v4.

Асимметрия правил, которую стоит знать при чтении валидатора: `$.campaign.xp` проверяется как «конечное неотрицательное **число**», а `$.character.xp` — как «неотрицательное **целое**», и третье правило требует их равенства. Дробный `campaign.xp` в v5 отклоняется поэтому не своим правилом, а парой «целое + равенство» — то есть целочисленность XP в v5 держится, но через cross-field, а не напрямую.

**Почему `unspentSkillPoints` начисляются, а не обнуляются.** Уровни были заработаны под старым сохранением, и до W4-03 очки никто не тратит. Обнуление молча удалило бы заработанную прогрессию, и обнаружилось бы это только когда появится экран траты очков.

**Почему на экране возврата подставляется `retreat`, а не `defeat`.** В v4 отступление *было* поражением: один и тот же переход, одна и та же `phase: 'defeat'`, — поэтому payload физически не содержит ответа. Догадка `defeat` начислила бы штраф XP за состояние, в которое игрок вошёл до появления штрафа, то есть наказала бы за обновление. Догадка `retreat` стоит максимум одного пропущенного штрафа, однократно, и только для сохранения, которое на момент обновления стоит на экране возврата; повториться это не может, потому что каждый последующий возврат записывает свою причину сам. Неоднозначность решена в пользу игрока и названа явно, а не оставлена неявной.

**Отклонение раньше миграции.** v4-источник валидируется **как v4** (`validateVersioned(input, 4, …)`) и только валидный повышается до v5. Реализация одна: правила, общие для двух версий, — один код-путь; два поля, которых в v4 нет, гейтятся по версии. Причина строгости: миграция, которая ремонтирует битый источник, неотличима от миграции, которая выдумывает прогресс.

Таблица миграции v5 → v6 (`normalizeV6`, `W6-01` ✅, 25 августа 2026). Добавлено ровно одно поле, ни одно существующее не переосмыслено:

| Поле v5 | Поле v6 | Правило | Дефолт |
|---|---|---|---|
| — | `objective` | новое состояние; прогресс посреди миссии **не выдумывается** | `{ heldTurns: 0, carrying: false }` |

**Почему нулевое состояние, а не догадка — даже для сохранения, застигнутого посреди миссии.** v5-payload появился раньше самих целей: каждая шиппящаяся миссия завершалась зачисткой карты, поэтому ни счётчика удержания, ни флага груза в нём нет — эта информация никогда не записывалась. Обнуление к тому же единственный вариант, который ничего не **выдаёт**: `carrying: true` подарил бы уже доставленный груз, а ненулевой `heldTurns` — готовое прохождение. Цена ограничена и однократна — игрок, застигнутый посреди `secure`, удерживает точку заново, — и платится в сторону, которую нельзя эксплуатировать.

**Цепочка стала длиннее, и каждая стадия по-прежнему проверяется своими правилами:** v3 → v4 → v5 → v6. Это не косметика — именно это не даёт переписать сохранение двухверсионной давности правилами, которым оно никогда не удовлетворяло. v5-источник валидируется как v5 и **минует стадию v4**, потому что он её уже прошёл.

**Путь v3.** Явный, не молчаливый: v3 → v4 → v5, каждая стадия проверяется правилами своей версии. v3-сохранение либо повышается, либо падает со списком проблем той стадии, на которой сломалось.

### 5.4 Явные ограничения защиты

Прямо и без смягчения: локальное сохранение защищено от **порчи и обычных ошибок потока**, но **не** от ручного отката или редактирования `localStorage`. Exactly-once награды гарантируется только в нормальном потоке приложения. Anti-tamper и авторитетные лидерборды требуют серверного сохранения, которого нет. Ни один документ и ни один PR не должен утверждать иное.

## 7. Реестр ассетов

Вводится в W8-02. Файл `art/registry.json`. Каталог `art/` создан в `W0-03` и пуст; правила именования файлов — [`art/README.md`](../art/README.md).

```json
{
  "contentVersion": 1,
  "kind": "asset-registry",
  "entries": [
    {
      "id": "hero-silhouette-a",
      "kind": "unit" ,
      "path": "art/units/hero-a.png",
      "size": { "width": 64, "height": 96 },
      "states": ["idle", "hit"],
      "author": "<имя>",
      "license": "<лицензия, локально проверенная>",
      "fallback": { "type": "shape", "color": "token:unit-player" }
    }
  ]
}
```

Правила:

1. Запись **без** `license` и `author` отклоняется. Прямое требование doc 19: внешние ассеты без локально проверенной лицензии не используются.
2. Каждая запись обязана иметь `fallback`. Отсутствие файла ассета не имеет права ломать игру.
3. Каждая UI-иконка обязана иметь монохромный fallback (требование doc 19).
4. Каждое критическое состояние (hit, miss, armor, status, overwatch, malfunction) обязано иметь sprite или shape fallback.
5. `id`, используемые в коде, и `id` в реестре обязаны совпадать множествами — проверяется тестом.
6. Цвета fallback ссылаются на design tokens (`token:*`), а не на литеральные hex.

Аудио-реестр — тот же формат с `kind: "audio"`, обязательными `license`, `author`, `durationMs` и `layer` (ui/combat/status/world/music) по матрице doc 15.

## 8. RNG, детерминизм и воспроизведение

Источник: `code/src/game/rng.ts`.

```ts
export const DEFAULT_RNG_STATE = 0x6d2b79f5
export function nextRandom(state: number): { state: number; value: number }
// LCG: next = (state * 1664525 + 1013904223) >>> 0; value = next % 100 + 1
```

Контракт:

| Правило | Обоснование |
|---|---|
| `rngState` — часть сохранения | случайность продолжается корректно после reload |
| Боевой pipeline **не** генерирует случайность внутри | `combatAttack` принимает `{ hit, crit, malfunction }` как аргументы |
| Значения в диапазоне 1..100 | вся боевая математика работает в процентах |
| RNG фазы врага сохраняется | resume после reload не «перебрасывает» кубики |
| Любой тест и симулятор фиксируют seed | воспроизводимость обязательна |
| AI не читает будущие броски | нельзя давать врагу информацию, недоступной игроку |

**Ограничение, которое нельзя скрывать:** LCG с `% 100` даёт лёгкое смещение и предсказуем. Для локальной одиночной игры это приемлемо. Для авторитетных лидербордов — нет. Замена генератора = смена контракта сохранения (изменится последовательность бросков) и требует повышения версии схемы.

**Формат отчёта симулятора** (реализован в `W3-01`/`W3-02`, каталог `design-data/balance/` — **заполнен** 23 августа 2026, правила — [`design-data/README.md`](../design-data/README.md)). Фактическая форма, `code/src/sim/report.ts`:

```json
{
  "commit": "51dc2e5ec1b3",
  "contentCatalogId": "m3-b-arenas-v1",
  "seed": 12345,
  "runs": 200,
  "policy": "cover-torso",
  "mode": "isolated",
  "turnLimit": 40,
  "arenas": [
    {
      "arena": "relay-station",
      "encounterId": "relay-station",
      "policy": "cover-torso",
      "metrics": {
        "runs": 200,
        "winRate": 0.73, "lossRate": 0.21, "ammoEmptyRate": 0.06, "turnLimitRate": 0.0,
        "turnsMean": 3.6, "turnsMedian": 3,

        "ttkByArchetype": { "sun-defender": 3.7397 },
        "ttkDetailByArchetype": { "sun-defender": { "count": 146, "mean": 3.7397, "median": 3, "min": 2, "max": 8, "stdDev": 1.3315 } },
        "damageTakenMean": 10.965, "ammoSpentMean": 4.255,
        "weaponDurabilityLostMean": 8.52, "armorDurabilityLostMean": 2.31,

```

Отличия от первоначального плана контракта, сознательные: `arena` — не корневое поле, а элемент массива `arenas[]`, потому что отчёт всегда покрывает весь живой набор encounter и обязан давать `total` по объединённому пулу (W3-02, критерий 2); добавлены `policy`, `mode`, `turnLimit` и `contentCatalogId`, без которых числа не воспроизводимы; добавлена секция `economy` (W3-03).

1. Отчёт обязан ссылаться на коммит: числа без коммита невоспроизводимы и не являются основанием для решений. Симулятор берёт SHA из `SIMULATE_COMMIT`, затем `GITHUB_SHA`, затем `git rev-parse`; если не разрешилось — пишет `null` и Markdown прямо предупреждает, что отчёт невоспроизводим. Провенанс не выдумывается.
2. В теле отчёта не должно быть ничего окружения: ни времени, ни путей, ни имени хоста. Дата допустима **только** в имени файла. Это то, что делает «один и тот же seed даёт побитово одинаковый отчёт» проверяемым утверждением, а не пожеланием.
3. Рядом с JSON лежит `.md` с теми же числами. Расхождение между артефактами — дефект: читатель не должен их сверять.

## 9. Владение данными и рабочий процесс автора контента

### 9.1 Владение

| Данные | Владелец | Кто утверждает изменение |
|---|---|---|
| Боевые формулы и константы | ведущий разработчик | владелец продукта после балансового прогона |
| Числа баланса (XP, стоимости, награды) | владелец продукта | balance lock v1 (W3-04) — **предложение** сформулировано 24 августа 2026 (doc 12 §«Предложение balance lock v1»), утверждения нет. Коридоры, в которых изменённые числа обязаны оставаться, закреплены тестами `W3-05` (`code/src/sim/bounds.ts`) |
| Каталог зон и encounter | владелец продукта | разработчик проверяет валидность |
| Файлы карт | автор контента | разработчик проверяет играбельность |
| Каталог экипировки | владелец продукта | разработчик проверяет ссылки и границы |
| Схема сохранения | ведущий разработчик | только через версию и миграцию |
| Реестр ассетов | **не назначен** — открытое решение doc 19 | требует назначения в W8-02 |
| Нарративные тексты | владелец продукта | ⛔ implementation spec отсутствует; в коде нет ни диалогов, ни NPC |
| Аудио-реестр | владелец продукта | ⛔ implementation spec отсутствует; в репозитории нет звуковых файлов |

### 9.2 Процесс добавления контента

1. Взять шаблон нужного `kind` (создаётся в W7-02).
2. Заполнить поля; все ссылки — на существующие id.
3. `npm run validate:content` — обязательно до коммита.
4. Для новой карты — `npm run validate:content -- --strict-playability` (достижимость, укрытия, ровно один герой).
5. Прогнать симулятор на новом encounter (W3-01) и приложить отчёт.
6. Добавить новой encounter коридор win rate в `WIN_RATE_CORRIDORS` (`code/src/sim/bounds.ts`). Без него `balance-bounds.test.ts` падает: encounter без утверждённого коридора считается нарушением, чтобы новый контент не мог молча выпасть из границ баланса.
7. Проверить, что `npm test` и `npm run test:e2e` зелёные.
8. В PR указать: что добавлено, какие ссылки затронуты, отчёт симулятора, что **не** проверено.

Правило: **контент не добавляется вместе с изменением кода в одном PR**, если только само изменение кода не требуется для нового вида контента. Смешивание делает невозможным откат контента без откатa механики.

### 9.3 Запрещено

- Добавлять контент, ссылающийся на несуществующие id, «пока временно».
- Обходить валидацию флагом или условием для «своих» файлов.
- Держать одно и то же число в JSON и в коде без теста синхронности.
- Менять `contentVersion` без функции миграции.
- Добавлять бинарные ассеты без записи в реестре с лицензией.
