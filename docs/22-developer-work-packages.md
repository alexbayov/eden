**Статус:** 🟢 v1.1, 23 августа 2026. Порядок выполнения — в [`21-delivery-plan-and-backlog.md`](21-delivery-plan-and-backlog.md).

## Как читать документ

Каждый тикет имеет фиксированную структуру:

- **Цель** — одно предложение.
- **Источники** — документы и файлы кода, задающие поведение.
- **В scope / вне scope** — граница работы.
- **Контракт данных/API** — что именно меняется в типах, JSON или публичных функциях.
- **Критерии приёмки** — проверяемые утверждения.
- **Тесты** — какие автоматические проверки обязательны.
- **QA** — ручные шаги, если они нужны.
- **Зависимости**, **Оценка** (S ≤ 0.5 дня, M ≈ 1–2 дня, L ≈ 3–5 дней), **Commit/PR**.

Общие требования ко всем тикетам:

1. Ветка `feat/<пакет>-<номер>-<краткое-имя>` или `fix/`, `chore/`, `docs/`, `test/` по типу работы.
2. Commit message: `<type>(<пакет>): <что и зачем>` в одну строку, тело — по необходимости.
3. PR обязан содержать разделы: **Что сделано**, **Что проверено**, **Что НЕ проверено**, **Затронутые документы**.
4. Ни один PR не мержится с красным `lint`/`typecheck`/`test`/`build`/`analyze:budget`.
5. **Запрещено** утверждать в коде, тестах, документах или PR, что браузерная/устройственная проверка состоялась, если её не было.
6. Изменение любой формулы или числа требует: владельца, версии, теста, обновления документа и кода в одном PR.

### Маркеры состояния

| Маркер | Значение |
|---|---|
| ✅ Ready | все зависимости и решения закрыты, можно брать |
| 🟡 Needs decision | ждёт решения владельца продукта (D-xx из doc 21 §9) |
| ⛔ Blocked (external) | требует ассетов, аудио или платформенной спецификации, которых нет |

## W1-05 — Проверки viewport и геометрии — ВЫПОЛНЕНО (23 августа 2026, не закоммичено)

**Фактическое состояние.** **35 тестов** зелёные в `viewport-geometry.spec.ts` + хелперы `e2e/helpers/geometry.ts`. Это первые фактические числа о геометрии в проекте.

Отклонение от исходного контракта, сделанное осознанно: **`page.setViewportSize` в теле теста вместо пяти Playwright-проектов.** Пять проектов множили бы весь набор E2E на пять ради того, чтобы прогонять smoke и save-тесты на размерах, к которым они не относятся. Матрица построена как `for` по viewport × экран внутри одного проекта `chromium`; имя viewport и причина его включения попадают в имя describe-блока, поэтому отчёт читается так же.

**Покрытие расширено до пяти экранов.** Изначально измерялись три (`home`, `mission-select`, `combat`); добавлены `reward` и `return` — те два экрана, через которые игрок проходит **принудительно** после каждого encounter, и чьи главные CTA (`ЗАБРАТЬ НАГРАДУ`, `ВЕРНУТЬСЯ НА БАЗУ`) являются единственным выходом из них. Оба сохранения строятся тем же `buildSave`, поэтому проходят runtime-валидацию `validateSave` в момент сборки фикстуры, и оба CTA не только измеряются, но и **нажимаются** на 360×640 с переходом на `БАЗА`. Итого 5 viewport × 5 экранов = **25 измеренных комбинаций** геометрии.

**Результаты.**

- **Горизонтального переполнения нет** ни на одном из пяти viewport ни на одном из **пяти** экранов. Измеряется двумя способами: `scrollWidth` против `clientWidth` (документ и body) и правый край каждого элемента — второй ловит элемент, вылезающий из scroll-контейнера, не растягивая документ.
- **Ни один интерактивный элемент не меньше 44×44 CSS px** ни на одном viewport. Счётчик контролов не даёт «пусто» пройти за «нет нарушений». Селектор шире, чем `button` (`a[href]`, `input`, `select`, `textarea`, `[role=button]`), скрытые элементы пропускаются осознанно — их нельзя промахнуться.
- **Все шесть частей тела** на 390×844 присутствуют, имеют размер ≥44 px и реально переключаются кликом (проверяется класс `active`).

**Проверенные критерии приёмки.**

1. ✅ Ни один интерактивный элемент не меньше 44×44 px по **измеренному** размеру на каждом viewport.
2. ✅ Горизонтального скролла нет ни на одном viewport.
3. ✅ **Выполнен на ширинах телефона** (360×640 и 390×844) для **всех пяти** экранов, ❌ **не выполнен на трёх более широких viewport**. Критерий сформулирован для 360×640 — там он выполняется полностью.

   Причина, по которой это работает: блок `@media (max-width: 760px)` переводит главное действие каждого экрана в закреплённую нижнюю полосу (`position: fixed`, `bottom: calc(12px + env(safe-area-inset-bottom))`). Поэтому CTA стоит на y=584 (360×640) и y=788 (390×844) независимо от высоты страницы.

   **Явно зафиксированная политика:** закреплённый CTA **считается** находящимся в пределах первого экрана, когда он действительно виден без прокрутки. Поэтому `withinFold` всегда проверяется в паре с `toBeInViewport` — геометрический прямоугольник сам по себе не доказал бы, что элемент не перекрыт и не обрезан. Для `reward` и `return` дополнительно проверяется нажатие без прокрутки.

   Измеренные значения `y` (высота CTA везде 44 px):

   | viewport | home | mission select | combat | reward | return |
   |---|---|---|---|---|---|
   | 360×640 | ✅ y=472 | ✅ y=584 fixed | ✅ y=584 fixed | ✅ y=584 fixed | ✅ y=584 fixed |
   | 390×844 | ✅ y=472 | ✅ y=788 fixed | ✅ y=788 fixed | ✅ y=788 fixed | ✅ y=788 fixed |
   | 768×1024 | ✅ y=503 | ❌ y=1457 | ❌ y=1738 | ❌ y=1756 | ❌ y=1756 |
   | 1280×720 | ✅ y=503 | ❌ y=1437 | ❌ y=897 | ❌ y=1736 | ❌ y=1736 |
   | 800×400 | ❌ y=503 | ❌ y=1457 | ❌ y=1517 | ❌ y=1756 | ❌ y=1756 |

   **800×400 — политика заявлена явно, потому что случай двойственный.** Экран шириной 800 px находится **выше** breakpoint 760 px, поэтому закреплённой полосы не получает вообще, а высота 400 px меньше, чем шапка плюс панель над любым CTA. Поэтому здесь закреплять нечего, и тест утверждает **фактическое** измеренное значение: `false` на всех пяти экранах, включая базу.

   **1280×720 — исправление ранее задокументированного неверного числа.** Прежняя версия документа и baseline теста утверждали `mission-select: ✅ y≈420` на этом viewport. Измерение на текущей сборке даёт y=1437 (`false`). Причина: `.campaign-grid` больше не трёхколоночная сетка, а `display: flex; flex-direction: column`, поэтому три карточки кампании складываются в столбец на **любой** ширине, и mission select уезжает под сгиб и на desktop. Это проверено экспериментом: возврат старого правила `grid-template-columns` возвращает y=420 на 1280×720 — но одновременно ломает базовый CTA на 360×640 (y=670 при высоте 640, `false`). Старое число в документе относилось к другой вёрстке.

   Закрытие остатка разрыва требует изменения вёрстки (расширение breakpoint закреплённой полосы или правило по высоте для короткого landscape), а мандат `W1-05` — измерять без изменения вёрстки и геймплея. Поэтому измеренное состояние для трёх широких viewport **зафиксировано как baseline** (таблица проверяется целиком, случайный регресс упадёт), а ширины телефона проверяются как **требование**, а не как baseline. Отдельный тест доказывает, что боевой экран не является неработоспособным: на 360×640 игрок выбирает цель, стреляет, и `ОТСТУПИТЬ` тоже достижимо. Вёрстку правит будущий тикет — кандидаты `W2-02`, `W2-05`.
4. ✅ Все шесть частей тела доступны и работоспособны на 390×844.
5. ✅ `responsive-css.test.ts` остался, его комментарий обновлён: объяснено, что статические проверки теперь дополнены измерениями, и **почему оба слоя оставлены** (декларированный `min-height` ничего не говорит о том, сматчилось ли правило и не сжал ли контрол flex-родитель; обратно — статические проверки идут за миллисекунды и покрывают состояния, куда E2E не заходит: `prefers-reduced-motion`, `:focus-visible`). **Два определения, влияющие на чтение чисел.** TTK измеряется **в ходах игрока** (номер хода, на котором умер враг данного архетипа), а не в выстрелах или секундах; арена с двумя врагами даёт две выборки. # W10 — Платформа и релиз

## W10-01 — Спецификация платформенной совместимости 🟡 / ⛔

**Цель.** Заменить предположения о Яндекс.Играх фактами.

**Блокировка.** Локальной спецификации платформенных API нет. `00-critical-audit.md` §Платформа прямо фиксирует: совместимость рекламы, покупок, аналитики и облачных сохранений не подтверждена; ни одна интеграция не считается утверждённой.

**Что нужно от владельца.** Решение D-05 и доступ к актуальной документации платформы: доступные SDK-методы, требования к загрузке, ограничения хранилища, форматы рекламы, возрастные и consent-требования, требования к лидербордам.

**В scope (когда разблокируется).** Документ соответствия: требование платформы → как выполняется → чем проверено; выявление конфликтов с моделью no-P2W из doc 16.

**Критерии приёмки (когда разблокируется).** Каждое требование платформы отмечено выполненным, невыполненным или неприменимым; конфликты с doc 16 явно перечислены; ни одно требование не помечено выполненным без проверки.

**Оценка.** M (после разблокировки). **Зависимости.** D-05.

## W10-02 — SDK-абстракция с no-op по умолчанию ✅

**Цель.** Игра работает и вне платформы; интеграция подключается позже.

**Источники.** W10-01, `16-monetization.md`.

**В scope.** Интерфейс платформы (`init`, `saveCloud`, `loadCloud`, `leaderboard`, `ad`, `analytics`) с реализацией no-op по умолчанию; функциональность игры не зависит от наличия платформы; отсутствие сетевых запросов в no-op режиме.

**Вне scope.** Реальная интеграция (после W10-01). Реклама и покупки как механика.

**Контракт API.**

```ts
export interface Platform {
  readonly available: boolean
  init(): Promise<void>
  cloudSave?(payload: string): Promise<boolean>
  cloudLoad?(): Promise<string | null>
  submitScore?(board: string, value: number): Promise<boolean>
}
export const noopPlatform: Platform
```

**Критерии приёмки.**

1. Игра полностью проходится с `noopPlatform`.
2. Ни один игровой путь не блокируется отсутствием платформы.
3. В no-op режиме не выполняется ни одного сетевого запроса (проверяется E2E перехватом сети).
4. Никакой код игры не передаёт данные игрока третьим сторонам без явного действия пользователя.
5. Ошибка платформы деградирует безопасно, с сохранением локального прогресса.

**Тесты.** Полный happy path на no-op платформе; отсутствие сетевых вызовов. **QA.** E2E. **Зависимости.** W10-01 (частично; абстракцию можно писать раньше). **Оценка.** M.

**Commit/PR.** `feat(W10): add platform abstraction with safe no-op default`.
