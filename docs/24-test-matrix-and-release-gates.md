## 1. Честная граница текущей проверяемости

**Что проверено автоматически (факт на 22 августа 2026):** 17 тестовых файлов, 128 тестов, все проходят локально через `npm run verify`. Это статические и модельные проверки: чистые функции, фикстуры каталогов, валидация сохранений, view-model, чтение CSS и TSX **как текста**. Состав и число тестов не изменились после чистки мёртвых модулей в `W0-02`.

**Что не проверено вообще:**

| Область | Состояние | Почему |
|---|---|---|
| Рендеринг в браузере | не проверено | нет headless-браузера в `devDependencies` |
| Геометрия на любом viewport, включая 390×844 и 360×640 | не проверено | нет измерений; `responsive-css.test.ts` читает CSS как текст и сам это фиксирует в комментарии |
| Взаимодействие на реальных устройствах | не проверено | ручных прогонов не было |
| Runtime-производительность | не проверено | `analyze:budget` — статический gzip-гейт, не профиль |
| Доступность с ассистивными технологиями | не проверено | нет прогонов со скринридером |
| Платформенные интеграции | не проверено | интеграций не существует |

**Правило документа:** ни один тест, комментарий, документ или PR не имеет права утверждать проверку из второй таблицы, пока соответствующий тикет W1/W2 не закрыт.

1. Никакой реальной случайности: броски инжектируются, seed фиксируется.
2. Никакого реального времени: таймеры не используются или подменяются.

4. Каждый тест падает при откате изменения, которое он защищает — проверяется вручную при написании.

## 3. Уровень 2 — DOM и браузерные E2E (не существует, вводится в W1)

### 3.1 DOM-тесты (W1-02)

Окружение jsdom, только для `*.dom.test.tsx`. Поиск элементов по доступной роли и подписи, **не** по CSS-классу.

| Область | Обязательные проверки |
|---|---|
| Загрузка | загрузочный экран рендерится без доступа к кампании |
| Recovery | ошибка каталога и порча сохранения дают понятный экран |
| База | узлы, stash, переход к миссии |
| Mission select | статусы encounter, блокировка недоступных |
| Бой | контролы, breakdown, гейтинг горячих клавиш через реальный обработчик |
| Награда | итог нельзя пропустить незаметно |
| Настройки | изменение и применение опции |

### 3.2 E2E happy path (W1-03)

| Сценарий | Проверяет |
|---|---|
| Полное прохождение зоны | три encounter, порядок разблокировки, статус зоны |
| Победа и награда | exactly-once claim по UI и по `localStorage` |
| Поражение | статус `failed`, отсутствие награды, доступность retry |
| Отступление | доступно в фазе игрока, недоступно на enemy transition |
| Цикл базы | лут → крафт → ремонт → лечение → следующая вылазка |

### 3.3 E2E сохранения (W1-04)

| Сценарий | Ожидание |
|---|---|
| Reload на `available`/`active`/`completed` | то же состояние и то же XP |
| Порча JSON | recovery-экран + запись в `eden.save.v4.corrupt-backup` |
| Неизвестный encounter в сохранении | отказ с сообщением, приложение работоспособно |
| Недоступное хранилище | приложение не падает |
| Обновление схемы | сохранение прошлой версии продолжает игру |

Ни один сценарий не имеет права закончиться белым экраном.

### 3.4 Визуальный регресс (W1-08, опционально)

Пять экранов × два viewport. Обновление эталона требует явной причины в PR. Боевой канвас не покрывается: он недетерминирован без фиксации кадра.

## 5. Ручные тестовые скрипты

Каждый скрипт: предусловие → шаги → ожидаемый результат. Отчёт — в `design-data/qa/`.

### MS-01 — Первая сессия (10 минут)

1. Открыть игру в приватном окне (пустое хранилище).
2. Пройти онбординг, не читая документацию.
3. Завершить первый encounter.
4. Получить награду и вернуться на базе.

Ожидание: игрок понимает цель без внешних объяснений; ни одно действие не требует hover; экран награды не пропускается незаметно.

### MS-02 — Мобильный бой одной рукой

1. На телефоне начать encounter.
2. Выбрать все шесть частей тела через long-press radial menu.
3. Сменить позу, использовать Overwatch, применить расходник, перезарядиться.
4. Завершить бой.

Ожидание: все действия достижимы одной рукой; ни один элемент не меньше 44 px на ощупь; ничего не перекрыто вырезом или системной панелью.

### MS-03 — Персистентность

1. Начать encounter, сделать 2–3 хода.
2. Перезагрузить страницу.
3. Продолжить и завершить бой.
4. Перезагрузить на экране награды и забрать награду.

Ожидание: состояние, HP, статусы, магазин и XP не меняются; награда не выдаётся дважды.

### MS-04 — Цикл базы

1. Вернуться с лутом.
2. Скрафтить предмет, отремонтировать оружие, вылечиться, улучшить узел.
3. Проверить веса и вместимость.
4. Уйти в следующую вылазку.

Ожидание: каждая транзакция атомарна; стоимость видна до подтверждения; нехватка ресурсов объяснена.

### MS-05 — Клавиатура и доступность

1. Пройти полный цикл только с клавиатуры.
2. Проверить видимость фокуса на каждом элементе.
3. Включить высокий контраст, масштаб 150%, reduced motion.
4. Прослушать боевой лог скринридером.

Ожидание: ни один экран не требует мыши; фокус всегда виден; результат каждого выстрела доступен текстом.

### MS-06 — Деградация

1. Удалить ассеты (или заблокировать их загрузку) и пройти бой.
2. Испортить сохранение вручную и перезагрузить.
3. Отключить сеть после загрузки и продолжить игру.
4. Заполнить `localStorage` до отказа.

Ожидание: fallback работает; recovery-экран понятен; игра продолжается офлайн; переполнение хранилища не приводит к потере уже сохранённого прогресса без предупреждения.

## 7. Проверки доступности

### 7.1 Автоматические (axe в E2E, W2-04)

| Проверка | Критерий |
|---|---|
| Контраст основного текста | ≥ 4.5:1 |
| Контраст крупного текста и индикаторов | ≥ 3:1 |
| Контраст индикатора фокуса | ≥ 3:1 |
| Альтернативы изображений | каждое изображение подписано или декоративно |
| Именованные контролы | каждая кнопка имеет доступное имя |
| Порядок заголовков | без пропуска уровней |
| Live-области | результат действия попадает в live-область |
| Нарушения axe critical/serious | ноль |

### 7.2 Измеряемые в E2E (W1-05)

| Проверка | Критерий |
|---|---|
| Размер цели касания | ≥ 44×44 px по **измеренному** bounding box на всех viewport |
| Горизонтальный скролл | отсутствует на всех viewport |
| Доступность CTA | главный CTA виден без прокрутки на 360×640 |
| Масштаб 150% | нет перекрытий и обрезания |
| Независимость от hover | вся информация доступна без hover (усиление существующего статического теста) |

### 7.3 Ручные (W2-06, MS-05)

Клавиатурное прохождение, прогон со скринридером, проверка reduced motion, проверка «цвет не единственный канал».

> **Ограничение, обязательное к упоминанию:** полная валидация WCAG требует ручного тестирования с ассистивными технологиями и экспертного аудита доступности. Автоматические проверки и один прогон со скринридером этого не заменяют. Ни один документ проекта не должен заявлять о соответствии WCAG на основании автоматических проверок.

## 8. Классификация дефектов

| Severity | Определение | Примеры | Реакция |
|---|---|---|---|
| **S1 Blocker** | игра непроходима или прогресс теряется | белый экран, потеря сохранения, невозможно завершить encounter, награда выдаётся дважды | останов работы, исправление первым |
| **S2 Critical** | ключевая функция не работает или недоступна на целевом устройстве | бой невозможен на телефоне, CTA перекрыт, ввод не принимается, штраф смерти считается неверно | исправление до конца недели, гейт не закрывается |
| **S3 Major** | функция работает с обходным путём или заметно нарушен баланс | путаная ошибка, некорректный breakdown, дефицит ресурса делает крафт бессмысленным | исправление до следующего гейта |
| **S4 Minor** | косметика и мелкие неудобства | смещение на 1 px, опечатка, неидеальное выравнивание | бэклог |
| **S5 Trivial** | замечание без влияния на игрока | внутреннее имя, лишний лог | по возможности |

Правила: severity назначается по влиянию на игрока, а не по трудоёмкости; каждый дефект содержит шаги воспроизведения, ожидание, факт, устройство и коммит; дефект без шагов воспроизведения не считается дефектом; исправление S1/S2 обязано сопровождаться падающим до фикса тестом.

### 9.3 Правила гейтов

1. Гейт закрывается целиком; частичное закрытие не существует.
2. Закрытие гейта фиксируется с указанием коммита и даты.
3. Утверждение о ручной проверке требует отчёта с моделью устройства, версией ОС и браузера.
4. Не закрытый гейт останавливает начало следующей недели — сдвиг фиксируется в changelog `00-index.md`.
5. Провал гейта не «обходится» ослаблением критерия. Критерий меняется только явным решением владельца с записью причины.

## 10. Что не проверяется и не будет проверяться в MVP

Перечислено, чтобы отсутствие проверки не выглядело упущением:

| Область | Причина |
|---|---|
| Защита от ручного редактирования `localStorage` | требует серверного сохранения; прямо признано ограничением в doc 23 §5.4 |
| Авторитетность лидербордов | нет сервера |
| Нагрузочное тестирование | одиночная игра без сервера |
| Пентест | нет серверной части и нет обработки персональных данных |
| Локализация | только русский язык в MVP |
| Совместимость со старыми браузерами | целевые — актуальные версии |
| Автоматизированное тестирование на реальных устройствах | нет device farm; заменено ручной матрицей §4.2 |
